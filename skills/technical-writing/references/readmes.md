# README files

A README helps a reader decide whether a project fits their needs and reach a first useful result.
Keep it brief enough to scan.
Move detailed material to dedicated documentation and link to it.

## Choose the primary audience

A user-facing README should answer these questions early:

1. What does the project do?
2. Who is it for?
3. What can the reader accomplish with it?
4. How does the reader install or access it?
5. What is the shortest way to try it?

A developer-facing README may add the prerequisites and commands needed for common setup and use.
Keep contributor setup, maintenance procedures, architecture, and internal data flow in dedicated documentation.
Put exact API details in source or generated reference.

If a README serves both audiences, put user content first.
Place developer content in a clearly named section.

## Recommended content

Include sections that answer real reader needs:

- A short description of purpose and scope
- Installation or access requirements
- One complete example
- Expected output when it confirms success
- Links to detailed documentation
- Support, security, or license information when the project requires it

Omit empty standard sections.
Avoid badges, feature lists, or background sections that do not help readers evaluate or use the project.

## Examples and links

Use a common use case for the first example.
Keep the example complete and ready to copy.
Explain only details that readers need for the first result.

Link to reference overviews, generated API reference, contributing instructions, architecture documents, and advanced guides.
Use the README as an entry point for those documents.
